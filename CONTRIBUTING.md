# Как внести изменения в руководство

Руководство живёт по тем же правилам, что и код: любое изменение проходит через ветку, пул-реквест и ревью. Прямые коммиты в `main` запрещены.

## Как предложить изменение

1. Если правило спорное или затрагивает несколько разделов, сначала откройте issue с меткой `style-guide`. Опишите, где возникла путаница, и приложите пример текста.
2. Если правка мелкая (опечатка, неудачный пример), сразу делайте пул-реквест.
3. Создайте ветку от свежего `main`. Имя ветки: `<тип>/<кратко-о-чём>`, например `docs/accessibility` или `fix/glossary-typo`.

```bash
git switch main
git pull
git switch -c docs/accessibility
```

## Оформление коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание>

<тело, если нужно>
```

- Тип — на английском: `docs`, `feat`, `fix`, `ci`, `chore`, `refactor`.
- Область — раздел руководства: `style`, `format`, `glossary`, `templates`, `examples`, `lint`.
- Описание — на русском, со строчной буквы, в повелительном наклонении, без точки, до 72 символов.
- В теле объясняем, почему понадобилось изменение. Что изменилось, видно из дифа.

| Тип | Когда |
|---|---|
| `docs` | Новое или изменённое правило, страница, пример |
| `feat` | Новая возможность сайта или линтера |
| `fix` | Исправление ошибки в правиле, ссылке, линтере |
| `ci` | Изменения в GitHub Actions |
| `chore` | Зависимости, конфигурация, служебные файлы |

Примеры:

```text
docs(style): добавить правило для отрицательных сумм
fix(glossary): исправить определение перевода
ci: кешировать зависимости pip
```

## Процесс ревью

1. Откройте пул-реквест в `main` и заполните шаблон описания.
2. Дождитесь зелёного CI: markdownlint, проверка терминов и сборка `mkdocs build --strict`.
3. Нужно одно одобрение от участника, который не автор изменения.
4. Ревьюер проверяет:
    - правило решает реальную проблему и не противоречит другим разделам;
    - у правила есть уровень и пример «Плохо / Хорошо»;
    - сама страница написана по руководству.
5. Замечания исправляйте новыми коммитами, не переписывайте историю во время ревью. Когда замечание учтено, ответьте в треде и отметьте его как решённое.
6. После одобрения автор делает слияние через **Squash and merge**. Заголовок итогового коммита тоже в формате Conventional Commits.

После слияния GitHub Actions соберёт сайт и опубликует его на GitHub Pages. Проверьте вкладку Actions и сам сайт.

## Локальная сборка

Нужны Python 3.11+ и Node.js 20+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve
```

Сайт откроется на <http://127.0.0.1:8000>. Перед пушем запустите проверки, те же, что в CI:

```bash
make lint
make build
```

## Как добавить новый раздел

1. Создайте файл в подходящей папке `docs/`. Имя — латиница в нижнем регистре через дефис: `docs/style/accessibility.md`.
2. Начните страницу с заголовка первого уровня и абзаца о том, зачем раздел нужен.
3. Для каждого правила укажите уровень (**Обязательно** или **Рекомендуется**) и дайте пример.
4. Добавьте страницу в `nav` в `mkdocs.yml`, иначе её не будет в меню:

    ```yaml
    nav:
      - Текст:
          - Доступность текста: style/accessibility.md
    ```

5. Если в разделе есть примеры «как не надо», оберните их в `<!-- style-check: off -->` и `<!-- style-check: on -->`, чтобы линтер стиля их пропустил.
6. Если раздел вводит новые термины, добавьте их в `docs/glossary.md` и `scripts/terms.yml`.
7. Запустите `make lint` и `make build`, затем откройте пул-реквест.
